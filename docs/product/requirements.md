# プロダクト要求

- 状態: Draft
- 最終確認日: 2026-10-04
- 正本の対象: 期待する能力、優先度、受け入れ観点

ここでは、会話で確認された要求と、そこから導いた候補を分ける。`確定`は方向性として合意済み、`候補`は価値検証や追加判断が必要、`未決定`は実装を選べない状態を表す。`確定`でも MVP 採用を自動的には意味しない。

## 確定している要求

### PR-001 商品を中心に記録する

コーヒー、紅茶、スイーツの商品を登録し、判明した情報を後から更新できる。

受け入れ観点:

- 商品と体験が別の概念として扱われる。
- 体験をまだ記録していなくても商品を保持できる。
- カテゴリ固有の項目を持てる余地がある。

### PR-002 商品資料を複数保持する

パッケージ表裏、商品カード、店頭説明など、商品を理解するための写真・資料を複数関連づけられる。

受け入れ観点:

- 1 商品に複数のメディアを関連づけられる。
- メディアの意味や対象を後から判別できる。
- 商品資料と、特定の体験時だけの写真を区別できる余地がある。

### PR-003 同じ商品へ体験を追記する

飲む、食べる、淹れるなどの体験を、過去の記録を上書きせず商品へ複数追加できる。

受け入れ観点:

- 体験ごとに日時と自由記述を保持できる。
- 必要な場合だけカテゴリ固有の条件を追加できる。
- 過去の体験と新しい体験を比較できる形で保持する。

体験記録の構造:

- 共通情報は日時を自動記録し、行為、場所、写真は任意とする。
- 自分の感覚は自由記述を基本とし、香り・味・食感などのタグや評価軸は任意とする。
- 外部の説明は、自分の感覚と別欄・別データとして保持する。
- 同じ体験内で「淹れる前」「抽出直後」「冷めてから」など複数の観察を追加できる。
- カテゴリごとの詳細条件は、下記の「カテゴリ別の情報優先度」にある体験項目を使用する。
- 詳細条件、評価項目、星評価などの単一スコアは、体験を残すための必須入力にしない。

具体的な UI 文言、観察の入力形式、タグや評価軸の選択肢は実装設計時に決める。

### PR-004 情報の由来を区別する

商品の客観的属性、カードや店員など外部の説明、自分の観察・感覚を混同せず保持する。

受け入れ観点:

- 外部の説明には出典を関連づけられる余地がある。
- 自分の感覚を、外部説明の上書きとして保存しない。
- 画面上でも両者の違いを理解できる。

### PR-005 場所と役割を記録する

作り手の所在地、購入した場所、飲食した場所などを、役割の違いとともに商品または体験へ関連づけられる。

受け入れ観点:

- 商品に単一の「場所」を固定しない。
- 同じ場所を異なる役割で利用できる。
- オンラインの購入元を物理住所と無理に同一視しない。

場所情報の初期要件:

- 店名・住所を商品または体験へ関連づけて残せる。
- 商品記録時は、Google マップのキーワード検索のように店舗候補を探して選ぶ操作を想定する。
- Google マップは操作イメージを示す参考であり、サービスや API の採用を確定するものではない。
- 場所情報の保存に緯度・経度の指定を必須としない。
- 独立したマップ画面や、地図上のピンから関連する商品・体験を探索する機能は初期要件に含めない。

検索サービス、候補の選択・修正方法、検索で見つからない場所の入力方法、詳細画面での表示形式は実装設計時に決める。

### PR-006 軽く保存し、後から詳しくする

情報が不足していても記録を失わず、後で追記できる。ユーザーが残したい重要項目と、保存操作の必須項目を分ける。

受け入れ観点:

- カテゴリとして、コーヒー、紅茶、スイーツのいずれかを選ぶ。
- 写真 1 枚または仮の商品名のどちらかがあれば保存できる。
- 場所を含むその他の商品属性が不明でも保存できる。
- 情報が不足している記録は「詳細未入力」であることを後から判別できる。
- 追加項目の入力を、毎回の保存の前提にしない。

### PR-007 過去の記録を再発見する

商品情報、写真、時期、場所、カテゴリなどの手がかりから、過去の商品と関連体験を探して見返せる。

受け入れ観点:

- 正確な商品名を覚えていなくても探索経路がある。
- 商品を見つけた後、その資料、場所、体験へ辿れる。

再発見の初期要件:

- 写真を見ながら探せる商品一覧を提供する。
- 商品名、ブランド／作り手、商品属性、外部の説明、自分の感想を対象にキーワード検索できる。
- コーヒー、紅茶、スイーツのカテゴリで絞り込める。
- 購入・飲食した場所と時期で絞り込める。
- 商品から関連する写真、場所、体験へ移動できる。

専用の横並び比較画面や高度な検索は、利用状況を踏まえて具体化する。写真一覧は画像内容の自動認識や画像検索を必須とするものではない。

### PR-008 商品の同一性を管理する

Product は、カテゴリ、作り手／ブランド、商品名を手がかりに、ユーザーが同じ商品だと認識する単位とする。購入ごとの違いだけでは別 Product にせず、中身が明確に変わった場合は同じ商品系列に属する別 Product として扱う。

受け入れ観点:

- 焙煎日、購入日、価格、購入店、パッケージサイズが異なっても、それだけを理由に別 Product を強制しない。
- 産地、品種、精製方法、ブレンド、レシピなど商品の中身が明確に異なる場合は、別 Product として記録できる。
- 同系列の Product 同士を関連づけられる余地がある。
- 新しい記録を既存 Product へ追加するか、別 Product として作るかをユーザーが選べる。
- 誤って同一または別とした Product を、後から統合・分離できるようにする。
- システムは不確かな情報だけで同一商品と断定しない。

## カテゴリ別の情報優先度

ここでの優先度は、ユーザーが残したい情報の重要度を表す。保存操作の必須条件は PR-006 に従い、優先項目が不明でも保存できる。

### コーヒー

| 区分 | 情報 |
| --- | --- |
| 優先して残したい | 商品名、ロースター／ブランド、産地、品種、焙煎度、パッケージ・カード写真 |
| 分かれば残したい | 精製方法、農園、生産者、標高、ロット、収穫時期、焙煎日、ブレンド構成、商品 URL |
| 関連情報として残したい | 購入店、購入日、価格、購入 URL |
| 体験時に追記したい | 日時、場所、自分の感覚、抽出方法、湯温、粉量・湯量、挽き目、抽出時間 |

### 紅茶

| 区分 | 情報 |
| --- | --- |
| 優先して残したい | 商品名、ブランド／メーカー、紅茶の種類、産地またはブレンド・フレーバー名、パッケージ・カード写真 |
| 分かれば残したい | 茶園、生産者、品種、収穫時期、グレード、ロット、原材料、商品 URL |
| 関連情報として残したい | 購入店、購入日、価格、購入 URL |
| 体験時に追記したい | 日時、場所、自分の感覚、ホット／アイス／ミルク等の飲み方、湯温、茶葉量、湯量、抽出時間、抽出回数 |

### スイーツ

| 区分 | 情報 |
| --- | --- |
| 優先して残したい | 商品名、具体的な菓子種、パティスリー／ブランド／作り手、商品・パッケージ・説明カードの写真 |
| 分かれば残したい | 大分類となるジャンル、パティシエ、主な素材やフレーバー、構成、季節・期間限定情報、販売期間、商品 URL |
| 関連情報として残したい | 購入店、食べた店、購入・飲食日、価格、購入 URL |
| 体験時に追記したい | 日時、場所、自分の感覚、一緒に飲食したもの、持ち帰り／店内などの状況 |

`具体的な菓子種` はフィナンシェ、マドレーヌ、フロランタン、タルト、ショートケーキなどの粒度を指す。`ジャンル` は焼き菓子、生菓子、チョコレート、パフェ、ジェラートなどの上位分類であり、菓子種と混同しない。

## 品質要求の初期仮説

次は重要だが、測定基準は未決定である。

- **データ保全**: ユーザーの記録と写真を予期せず失わない。
- **入力継続性**: 正式に保存していない入力途中の記録を、画面遷移、再読み込み、ブラウザ終了、認証セッション切れの後も、一定の保持期間内であれば端末上で再開できるようにする。
- **データの正本**: 正式に登録された記録の正本はクラウドとする。端末上の復帰用下書きを、正式な記録や長期保存先として扱わない。
- **下書きのライフサイクル**: 記録確定操作前の入力下書きには保持期限を設ける。具体的な期間は、実装着手時に利用場面と端末容量を踏まえて決める。
- **送信待ちデータのライフサイクル**: 記録確定操作後の送信待ちデータは、クラウドへの反映が成功するか、ユーザーが明示的に破棄するまで自動削除しない。
- **操作完了の体感速度**: 記録確定操作を端末上で安全に受理できた時点で、ユーザーには操作が完了したものとして表示し、別の操作へ移れるようにする。クラウドへの反映は通常の操作フローを待たせずに進める。
- **内部状態の抽象化**: クラウドが正本であることや通常のアップロード状態を、ユーザーへ常時表示する要件とはしない。再試行などユーザーの対応が必要な例外だけを、理解しやすい形で通知する。
- **プライバシー**: 個人の行動、位置、写真を既定で公開しない。
- **可搬性**: 個人アーカイブを将来取り出せる手段を検討する。
- **アクセシビリティ**: 写真だけに情報を閉じ込めず、主要操作を支援技術から利用できるようにする。

未解決の判断は [open-questions.md](open-questions.md) で管理する。

`記録確定操作` は、ユーザーが入力を終えて記録を残す意思を示す操作を指す。ボタン、ジェスチャー、自動処理のいずれで実現するか、および「保存」「登録」などの UI 文言は未決定である。
