# ドメインモデル

- 状態: Draft
- 最終確認日: 2026-09-29
- 正本の対象: 共通語彙、概念の責務、関係、不変条件

これは実装スキーマではない。テーブル、クラス、API の形へ直接写経せず、技術選定とユースケースに合わせて設計する。

## 概念

| 概念 | 責務 | 例 |
| --- | --- | --- |
| **Product** | 記録の中心となる商品または提供物 | コーヒー豆、紅茶商品、ケーキ |
| **Product details** | カテゴリ固有の商品属性 | 産地、品種、焙煎度、茶園、菓子種別 |
| **Media** | 商品または体験に関する視覚資料 | パッケージ表裏、商品カード、店頭メニュー、体験写真 |
| **Experience** | Product に対して繰り返し発生する行為・観察 | 購入、飲食、抽出、試飲 |
| **Place** | 物理的またはオンラインの場所・入手先 | ロースター、店舗、カフェ、EC サイト、自宅 |
| **Party** | 商品を作る、焙煎する、販売する主体 | ブランド、ロースター、パティスリー、生産者 |
| **External description** | 他者が述べた説明とその由来 | 商品カードの説明、店員の説明、メーカー記載 |
| **Personal observation** | ユーザー自身が感じたこと | 香り、味、温度変化、自由な感想 |

`Party` と `Place` を同一概念にするかは未決定である。ブランドと店舗は一致しないため、少なくとも役割の違いは失わない。

## 関係

```text
Product 1 ─── * Experience
   │                │
   ├──── * Media    ├──── * Media
   │                ├──── * Personal observation
   ├──── * External description
   │
   └──── * Product–Place/Party relation (role付き)

Experience ─── * Experience–Place relation (role付き)
```

場所との関係には、少なくとも「作られた・焙煎された」「購入した」「飲食した」の違いがある。関係を単一の `product.place` に潰さない。

## 不変条件

- Experience は必ず 1 つの Product に属する。
- Product を更新しても、過去の Experience を暗黙に上書きしない。
- Product は Experience がなくても存在できる。
- Media は何を写した資料か、Product と Experience のどちらに属するかを判別できる。
- External description と Personal observation は別の情報として保持する。
- 不明な値と「該当しない値」を区別できる設計にする。
- 場所との関連には役割を持たせ、1 商品に複数の場所を関連づけられるようにする。

## カテゴリ差の例

| カテゴリ | 特徴づける候補属性 |
| --- | --- |
| コーヒー | 国・地域、農園、生産者、品種、精製方法、焙煎度、焙煎日、ブレンド |
| 紅茶 | 産地、茶園、茶葉種、収穫時期、グレード、ブレンド、フレーバー |
| スイーツ | 種類、作り手・パティスリー、季節性、主要素材 |

この表は入力必須項目を定めない。カテゴリごとの優先項目はユーザー検証後に決める。

## 同一性に関する未決定

同名商品、ロット、焙煎日、季節、店舗差を Product の別個体として扱う境界は未決定である。実装では、同一性を不可逆に固定する前に [open-questions.md](open-questions.md) の OQ-001 を解消する。
